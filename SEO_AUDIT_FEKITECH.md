# Fekitech SEO, content, technical and light-security audit

Audit date: 18 July 2026  
Production site: https://fekitech.co.uk/  
Search Console evidence: previous three months, supplied by the site owner

> **Owner-directed update:** After the evidence-led implementation, the site owner requested restoration of the original homepage metrics, testimonial marquee and About page wording. Those sections are therefore present again in the current build. The numerical outcomes and testimonial identities remain unverified by repository evidence and should be supported with approved records before relying on them as trust signals. A second business address at 10 Brindley Place, Birmingham, B1 2JB was also added as owner-supplied information.

## Executive summary

Fekitech has a sound crawlable foundation: public routes are prerendered to static HTML, route-specific titles, descriptions, canonicals, Open Graph data and JSON-LD are present in the initial response, the sitemap is generated from the same route data, and all 25 baseline sitemap URLs returned HTTP 200 during the live audit. The baseline production build and `npm run seo:check` both passed.

The highest-risk problems are trust and intent issues rather than an indexing block:

1. The homepage publishes unsupported numerical outcomes and duplicate promotional testimonials with stock portraits. Crawlers see the animated metrics as `0%`/`0x` in the initial HTML.
2. `FAQPage` schema is emitted on every article and dedicated service page even though Fekitech is not an eligible government or health authority. Existing tests incorrectly require this markup.
3. `/blog` uses the newest article title as its H1, so the index intent changes whenever a post is added. `/blog/all` is a near-duplicate self-canonical index.
4. Contact and About are thin and the primary enquiry language varies between a free call, audit and support request.
5. Commercial pages do not consistently link to their supporting guides.
6. The configured `www` redirect is not active in production: the `www` homepage returned 200 with an apex canonical rather than a permanent redirect.

No implementation can guarantee rankings, traffic or enquiries. The work below is designed to improve clarity, crawlability, trust, topical relationships and qualified conversion paths while protecting the pages that already rank well.

## Search Console interpretation

Protect the existing intent of the homepage (position 2.1), Services (4.8), Pricing (6.4), About (5.4) and the profitability article (5.4). These pages will receive small, evidence-led additions rather than aggressive title, H1 or intent changes.

The Contact page (position 8.9) and Blog index (8.1) have the clearest CTR and intent opportunity. Their titles, descriptions, stable H1s and explanatory copy are high priority.

The Business Intelligence, AI Agents and Website Automation articles already receive impressions but rank between positions 40.7 and 59.2. They will retain their URLs and informational intent while receiving targeted relevance, internal links and clearer commercial pathways. Two distinct commercial-investigation/comparison articles will cover the supplied gaps without merging or renaming existing pages.

## Architecture inventory

- Framework: React 19 with Vite 6.
- Routing: a small pathname router in `src/App.jsx`; crawlable navigation uses normal `<a href>` elements.
- Rendering: build-time prerendering. Vite creates the client bundle and a server entry; `scripts/postbuild.mjs` renders every configured route to `dist/<route>/index.html`.
- Hydration: `src/main.jsx` hydrates prerendered markup when present and falls back to client rendering in development.
- Metadata: central `pageSeo` records in `src/lib/site.js`, rendered server-side and maintained on client navigation by `src/lib/seo.js`.
- Blog source: `src/blogPosts.js` combines `src/newBlogPosts.js` and its existing-post records, then sorts them by real publication date. The same array drives listing, article rendering, metadata and sitemap inclusion.
- Services source: 12 substantial records in `src/serviceData.js` drive dedicated service pages and service routes.
- Sitemap and robots: generated by `src/lib/seo.js` during build. The sitemap is copied to `public/sitemap.xml`; robots was previously written only to `dist/robots.txt`, leaving `public/robots.txt` stale.
- Structured data: a shared JSON-LD `@graph` generated by `src/lib/seo.js` and included in initial HTML.
- Analytics: no first-party analytics implementation was found in the inspected source. Search Console data was supplied manually.
- Images: local PNG/WebP assets with explicit dimensions; a remote R2 homepage video; stock Pexels portraits were used only by the unsupported testimonial section.
- Forms: React contact form posts JSON to `/api/contact`; Cloudflare Turnstile is verified on the server; inputs are length-limited and HTML-escaped for email output.
- Deployment: Vercel configuration, prerendered static routes and serverless API handlers.
- Environment variables: server-only secrets cover Turnstile, Resend, PostgreSQL, admin sessions/passwords, cron and OpenRouter. The Turnstile site key is deliberately exposed through a server endpoint; secret keys remain server-side.
- Commands: `npm run build`, `npm run seo:check` and `npm run index:chatbot`. No test, formatter, linter or static type-check command is currently defined.
- Existing SEO utilities: prerender pipeline, metadata/schema utility, generated sitemap/robots, and deterministic SEO QA script.

## Metadata and on-page baseline

- Every sitemap route has one unique title, description, self-referencing absolute apex canonical, robots directive, Open Graph set and Twitter large-card set in initial HTML.
- `meta keywords` is emitted on every page. This conflicts with the brief and has no Google Search value; removal is planned.
- Homepage, Services, Pricing and About metadata matches their established broad intent and will be protected.
- Contact title/H1 and enquiry labels are inconsistent with the requested free business audit journey.
- Blog title and description are too broad for the demonstrated topic set, and its H1 is incorrectly borrowed from the featured article.
- `/blog/all` receives `og:type=article` even though it is a collection.
- Article titles/H1s are unique and descriptive; organisation-only authorship is visible and truthful. No human author will be invented.

## Structured-data baseline

Every public page currently repeats `Organization`, a combined `ProfessionalService`/`LocalBusiness`, `ContactPoint`, `WebSite` and `WebPage`. Inner pages also receive `BreadcrumbList`.

Route-specific schema includes:

- Homepage: unsupported `VideoObject` with a hard-coded 2024 publication date and generic thumbnail.
- Services overview: 12 `Service` nodes from a separate hard-coded list.
- Service detail pages: `Service` and `FAQPage`.
- Pricing: `OfferCatalog` with duplicated pricing data.
- Articles: `BlogPosting` and `FAQPage`.

Planned corrections:

- Keep visible question-and-answer content but remove every `FAQPage` block.
- Simplify to one verified `Organization` entity. Do not assert `LocalBusiness` until the address is confirmed as a genuine customer-facing operating location.
- Remove the unsupported `VideoObject` until its real upload date and representative thumbnail are verified.
- Point `BlogPosting.mainEntityOfPage` to the existing `#webpage` identity.
- Derive service schema from the visible service records.
- Keep semantic `Service` and `OfferCatalog` only where they match visible, genuine offerings; do not claim unsupported rich-result eligibility.
- Use truthful `AboutPage`, `ContactPage` and `CollectionPage` subtypes where appropriate.

This follows Google's requirement that structured data represent visible, relevant and current content: https://developers.google.com/search/docs/appearance/structured-data/sd-policies

## Light-security and reliability baseline

Verified strengths:

- No committed secret values were found in the targeted source scan.
- Turnstile secret verification occurs server-side.
- Contact inputs are length-limited, email format is checked, request bodies are capped, database writes are parameterised, and HTML email output is escaped.
- API secrets are read from server environment variables.
- Admin cookies are HTTP-only, secure outside localhost and SameSite=Lax.
- Admin data endpoints require a signed session and use no-store responses.

Verified risks/gaps:

- Contact, chat and admin abuse controls are process-local or absent. Persistent serverless rate limiting and admin MFA need infrastructure/owner decisions and are not safe to invent in this patch.
- Contact metadata stores IP and user agent. A privacy notice and approved retention policy are required; no privacy route currently exists.
- Default contact notifications include personal Gmail addresses. Replace them with approved controlled business mailboxes through deployment configuration.
- Production already sends HSTS, but other protective headers are absent. Safe global headers can be added; CSP should begin in report-only mode because Turnstile and the remote video require explicit origins.
- The static 404 page immediately redirects visitors with JavaScript instead of providing useful navigation.
- Current dependency vulnerability status remains unverified until `npm audit` can reach the advisory service.

## Measured performance evidence

No CrUX or field Core Web Vitals were available. PageSpeed API requests returned HTTP 429 because its daily query quota was zero, so formula-based output was discarded and is not presented as measurement. Lighthouse 12.8.2 simulated-mobile lab results were:

| Page | Performance | LCP | TBT | CLS | Transfer |
|---|---:|---:|---:|---:|---:|
| Homepage, run 1 | 69 | 4.9 s | 80 ms | 0 | 3,069 KiB |
| Homepage, run 2 | 62 | 5.2 s | 30 ms | 0 | 2,788 KiB |
| Contact | 99 | 1.8 s | 10 ms | 0 | 316 KiB |
| Blog | 96 | 2.4 s | 0 ms | 0 | 290 KiB |

Clean desktop reruns scored 96–99 with 0.7–0.8 s LCP, although the homepage transferred 8.3 MiB. The repeat mobile homepage result is the actionable signal: its LCP is the hero H1, with material render delay, and media dominates transfer. INP is unavailable and was not inferred from TBT.

The external R2 hero MP4 is 60,562,098 bytes, range-loads, and had no cache header during audit. It should be re-encoded into smaller mobile/desktop versions, served from versioned URLs with a long cache lifetime, and given a poster-only fallback for reduced-motion/reduced-data users. This needs an asset/deployment decision and was not silently replaced. Route-level CSS/animation splitting is a secondary opportunity because TBT is already low.
